3. Deployment Options

Option A: Deploy on Your Own Domain

  1. Create or select a GitHub repository for the white-label application.
  2. Upload the frontend files: index.html, app.js, styles.css, config.js, and related assets.
  3. Enable GitHub Pages from repository settings.
  4. In your domain provider DNS settings, create a CNAME record pointing your subdomain to your-github-username.github.io.
  5. Add the custom domain in GitHub Pages settings.
  6. Enable HTTPS after GitHub verifies DNS.

Option B: Deploy with GitHub Pages URL

  1. Create a GitHub repository, for example expense-tracker.
  2. Commit the application files to the main branch.
  3. Open repository Settings, then Pages.
  4. Select the branch and root folder for deployment.
  5. Save the Pages configuration.
  6. Open the generated URL, usually https://username.github.io/repository-name/.
After deployment, update config.js with the production Google Apps Script Web App URL.

4. Google Sheets Backend Setup

  1. Create a new Google Sheet for the application database.
  2. Create tabs for users, sessions, projects, categories, cash-in records, cash-out records, transactions, settings, backups, and audit history.
  3. Open Extensions, then Apps Script.
  4. Paste the FastStack backend Apps Script code into Code.gs.
  5. Set script properties for spreadsheet ID, backup folder ID, security keys, and allowed frontend origin.
  6. Deploy the Apps Script project as a Web App.
  7. Set "Execute as" to the script owner and access to the intended audience.
  8. Copy the Web App URL and place it in frontend config.js.

Backend Security Checklist

  • Do not expose the spreadsheet URL directly to application users.
  • Use the Apps Script Web App as the only bridge between frontend and Google Sheets.
  • Validate email, password, amount, date, category, and text fields server-side.
  • Sanitize input against formula injection by escaping values beginning with =, +, -, or @.
  • Use session tokens and reject expired or invalid sessions.
  • Keep admin-only operations protected.

5. Automated Backup Setup

  1. Create a dedicated Google Drive folder named after your white-label application.
  2. Copy the folder ID from the Drive URL.
  3. Add the folder ID to Apps Script properties.
  4. Run the backend setup function once to create or verify required sheets and backup configuration.
  5. Create a time-driven Apps Script trigger for daily backups.
  6. Use a retention policy of 30 days, or adjust according to your business policy.
  7. Test "Backup Now" from the app and confirm a backup file appears in Drive.
  8. Test restore on a copy of the sheet before using restore in production.
Recommended schedule: daily at a low-traffic time such as 2:15 AM in the operating timezone.

7. User Management and Security

  • Allow only authorized email domains if the deployment is internal.
  • Require strong passwords and email verification for new accounts.
  • Use role-based access for admin, manager, and standard users where needed.
  • Review user accounts regularly and disable inactive accounts.
  • Keep Apps Script deployments and script properties private.
  • Do not commit secrets, tokens, spreadsheet IDs, or private URLs into public repositories unless they are intended to be public.
  • Audit high-risk actions such as restore, delete, password changes, and admin changes.

8. Maintenance and Support

  • Check GitHub Pages deployment status after every update.
  • Review Apps Script execution logs for failed API calls.
  • Monitor Google Drive storage and backup retention.
  • Test login, registration, cash-in, cash-out, PDF export, and backup restore after major changes.
  • Keep a copy of the last known good frontend and backend code.
